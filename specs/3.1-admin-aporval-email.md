# SPEC 3.1 — Correo de aprobación de accesos para admin

> **Status:** Implemented
> **Depends on:** SPEC 03
> **Date:** 2026-11-14
> **Objective:** Crear un correo mock de solicitud de acceso para el admin, fiel a `resources/03_admin_approval_email`, con HTML transaccional, preview integrado y acciones mock preparadas para una futura validación server-side.

## Scope

**In:**

- Mantener `SPEC 03` sin ampliar su alcance funcional.
- Generar una notificación mock dirigida a `admin@jmmcdevsign.es` al crear una solicitud `pending`.
- Reproducir la composición visual de `resources/03_admin_approval_email`:
  - monograma y registro técnico;
  - asunto y mensaje de nueva solicitud;
  - tabla de datos del solicitante;
  - bloque de código de verificación;
  - acciones de aprobar y rechazar;
  - aviso de seguridad;
  - footer editorial.
- Crear un renderer HTML autocontenido y responsive, preparado para clientes principales y limitado a un canvas de 600 px.
- Crear un renderer de texto plano asociado al HTML para dejar preparado el envío transaccional.
- Compartir un modelo tipado entre la bandeja mock, el HTML transaccional y el preview web.
- Integrar el preview dentro del detalle de `/es/admin/approval`.
- Permitir alternar entre vista clara y oscura en el preview.
- Mantener el correo en español y adaptar dominios, destinatarios y valores al proyecto.
- Incluir nombre, correo, método de registro, fecha/hora, ciudad aproximada, IP fixture, dispositivo e identificadores de transacción y evento.
- Crear URLs mock para aprobar y rechazar con `requestId`, acción y token.
- Procesar las acciones mock con el admin fixture único.
- Cubrir los estados de acción aplicada, decisión repetida, token inválido y token expirado.
- Marcar la solicitud como `rejected` al ejecutar un rechazo válido.
- Registrar un evento mock de auditoría para cada intento de decisión.
- Mantener el código real de verificación fuera del correo admin previo a la aprobación.
- Conservar un código fixture únicamente en el preview para reproducir la referencia visual.
- Mantener todo el flujo sin llamadas a red ni proveedores externos.

**Out of scope (for future specs):**

- Enviar correos reales al admin o al usuario.
- Seleccionar o conectar Resend, SendGrid, SES u otro proveedor.
- Ejecutar acciones con autorización real server-side.
- Firmar tokens con una clave de producción o persistirlos en una base de datos real.
- Implementar migraciones, tablas, RLS, Edge Functions o endpoints propios.
- Enviar una notificación de rechazo al solicitante.
- Cambiar la política de expiración del código de verificación definida en SPEC 03.
- Implementar compatibilidad pixel-perfect específica para Outlook.
- Añadir idiomas distintos del español.
- Crear una ruta administrativa nueva fuera de `/es/admin/approval`.

## Data model

La spec reutiliza `RegistrationRequest`, `RegistrationStatus`, `EmailService` y la bandeja mock definidos en SPEC 03. Amplía sus contratos para representar el correo de aprobación sin introducir persistencia remota.

### Metadatos del correo

```ts
type AdminApprovalEmailMetadata = {
  approximateCity: string;
  ipAddress: string;
  device: string;
  transactionId: string;
  eventId: string;
};
```

Los valores de ciudad, IP y dispositivo son fixtures explícitos. En producción deberán provenir de una operación server-side validada y no de datos enviados por el cliente.

### Código mostrado en el correo

```ts
type AdminApprovalEmailCode =
  | { status: "pending"; label: "PENDIENTE DE EMISIÓN" }
  | { status: "fixture"; value: string; expiresInMinutes: 15 };
```

Una notificación creada al registrar la solicitud usa `pending`. El preview puede usar `fixture` para conservar el bloque visual de la referencia. El código operativo continúa perteneciendo a `VerificationChallenge` y solo se emite después de aprobar.

### Acciones mock

```ts
type AdminApprovalAction = "approve" | "reject";

type AdminApprovalEmailAction = {
  action: AdminApprovalAction;
  requestId: string;
  token: string;
  url: string;
  expiresAt: string;
};
```

La URL tendrá este formato lógico:

```text
/es/admin/approval?action=approve&requestId=req-001&token=mock-token
/es/admin/approval?action=reject&requestId=req-001&token=mock-token
```

El token es válido únicamente para el mock, se asocia al admin fixture y no se considera una autorización de producción.

### Modelo compartido

```ts
type AdminApprovalEmailModel = {
  request: RegistrationRequest;
  metadata: AdminApprovalEmailMetadata;
  code: AdminApprovalEmailCode;
  approveAction: AdminApprovalEmailAction;
  rejectAction: AdminApprovalEmailAction;
  sentAt: string;
  recipient: string;
};
```

### Evento de decisión

```ts
type ApprovalDecision = "approved" | "rejected";

type ApprovalDecisionEvent = {
  id: string;
  registrationRequestId: string;
  decision: ApprovalDecision;
  actorUserId: string;
  occurredAt: string;
  source: "admin-panel" | "admin-email";
  result: "applied" | "already-decided" | "invalid-token" | "expired-token";
};
```

Los eventos se almacenan en el repositorio mock únicamente para verificación local.

### Contratos públicos modificados

El contrato de correo de SPEC 03 se ajustará para que la notificación admin reciba el modelo completo:

```ts
interface EmailService {
  notifyAdmin(model: AdminApprovalEmailModel): Promise<void>;
  sendVerificationCode(
    request: RegistrationRequest,
    code: string,
  ): Promise<void>;
}

type RenderedEmail = {
  html: string;
  text: string;
};

type AdminApprovalEmailTheme = "bone" | "dark";

function renderAdminApprovalEmail(
  model: AdminApprovalEmailModel,
  theme?: AdminApprovalEmailTheme,
): RenderedEmail;
```

El método `notifyAdmin` seguirá siendo la frontera que consume el servicio de registro, pero dejará de recibir solo `RegistrationRequest`. La implementación mock guardará HTML y texto plano en la bandeja; un provider futuro podrá reutilizar `RenderedEmail`.

## Implementation plan

1. Crear los tipos `AdminApprovalEmailMetadata`, `AdminApprovalEmailCode`, `AdminApprovalEmailAction`, `AdminApprovalEmailModel` y `ApprovalDecisionEvent` en el dominio de autenticación.
2. Actualizar `RegistrationRequest` con `rejectedAt` y `rejectedBy` opcionales, manteniendo compatibilidad con las solicitudes existentes.
3. Cambiar `EmailService.notifyAdmin` para recibir `AdminApprovalEmailModel` y adaptar el servicio mock de registro para construir el modelo al crear una solicitud `pending`.
4. Añadir los metadatos mock, identificadores de evento/transacción y acciones con tokens mock expirables.
5. Implementar `renderAdminApprovalEmail` con HTML autocontenido, estilos compatibles con email, wrapping responsive y variante estable `bone` para el correo almacenado.
6. Implementar el texto plano asociado al HTML y guardar ambos formatos en `mockEmailInbox` sin eliminar el correo de código existente.
7. Crear el preview web dentro de `/es/admin/approval`, usando el mismo modelo y permitiendo alternar `bone`/`dark`.
8. Implementar el handler mock de acciones desde query params y desde los botones del preview; usar `MOCK_ADMIN_USER_ID` como actor.
9. Aplicar las decisiones de forma idempotente: aprobar genera el `VerificationChallenge` y envía el código al usuario; rechazar marca la solicitud como `rejected`; una solicitud ya decidida no se vuelve a mutar.
10. Registrar `ApprovalDecisionEvent` con el resultado correcto para acciones aplicadas, repetidas, inválidas o expiradas.
11. Documentar la frontera de producción: firma server-side, expiración, autorización, provider adapter y obtención segura de metadatos.
12. Añadir tests unitarios, de componentes y E2E; ejecutar typecheck, lint, tests, build y pruebas visuales en 375 px y 1440 px.

## Risks

| Risk | Mitigation |
| --- | --- |
| Los enlaces mock podrían confundirse con autorización real | Etiquetar el flujo como mock y documentar que producción debe validar firma, actor, expiración y estado en servidor. |
| La referencia contiene un código antes de que el flujo actual lo emita | Separar el código fixture del `VerificationChallenge` real y mostrar `PENDIENTE DE EMISIÓN` en el correo pendiente. |
| El HTML puede divergir del preview | Compartir `AdminApprovalEmailModel` y verificar ambos formatos con los mismos fixtures. |
| Los metadatos de IP o dispositivo podrían convertirse en datos de usuario reales | Mantenerlos como fixtures locales y prohibir que el cliente los presente como evidencia confiable en producción. |
| Cambiar `notifyAdmin` puede romper el servicio mock actual | Actualizar contrato, implementación y tests en el mismo cambio; conservar `sendVerificationCode` sin cambios. |
